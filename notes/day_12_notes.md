# Day 12 — Tokens, tokenization, context windows, model inputs and outputs

**Phase 2 | Beginner | 2–3 hours | Project: LLM Token and Context Window Analyzer**

## Learning outcomes
Explain tokens and tokenization; compare word and token counts; inspect token IDs using a suitable tokenizer; explain context windows; calculate an input/output budget; and describe strategies for oversized requests.

## 1. What is a token?
An LLM does not normally receive human-readable words directly. Text is converted into token IDs. A token can represent a complete common word, part of a word, punctuation, whitespace or another text unit.

**One token is not always one word.** Rare words may split into several pieces. The exact result depends on the tokenizer used by the selected model.

## 2. Tokenisation flow
~~~text
Human text → model-associated tokenizer → token pieces → token IDs → model input
~~~
Different models can use different tokenizers. A tokenizer from another model may provide only an estimate.

## 3. Why developers care
Token counts can affect:
- whether a request fits the context capacity;
- how much instruction, conversation history and retrieved information can be sent;
- output limits;
- latency and cost, depending on provider pricing.

Check current model/provider documentation for actual limits and pricing. They change and may account for categories differently.

## 4. Context window
A context window is the amount of tokenised information a model can consider in an interaction. Depending on the API, the budget may include system/developer instructions, chat history, user input, retrieved passages and generated output.

~~~text
Available context capacity (model-specific)
+----------------------------------------------+
| Instructions | History | User | Retrieved   |
|              |         | input| context     |
|              |         |      | + output    |
+----------------------------------------------+
~~~
This is a conceptual diagram, not a universal allocation rule. Some APIs define input and output limits separately.

If content exceeds limits, a request may fail or the application may need to shorten history, summarise older turns, retrieve fewer relevant passages or reduce output allowance. Do not silently discard important facts.

## 5. Input and output tokens
- Input tokens: instructions, context and user content supplied to the model.
- Output tokens: content generated by the model.
- Provider billing may distinguish input, cached input and output. Follow that provider's current accounting rules.

Example: 500 input + 120 output = 620 combined tokens for simple planning. The actual bill follows provider usage reporting and pricing.

## 6. Inspect tokenisation with tiktoken
This library demonstrates a supported encoding; it is not the tokenizer for every model.

Install in your virtual environment:
~~~bash
python -m pip install tiktoken
~~~

~~~python
import tiktoken

text = "Generative AI helps developers build useful applications."
encoding = tiktoken.get_encoding("cl100k_base")
token_ids = encoding.encode(text)
pieces = [encoding.decode([token_id]) for token_id in token_ids]

print("Text:", text)
print("Token count:", len(token_ids))
print("Token IDs:", token_ids)
print("Token pieces:", pieces)
~~~

Line by line:
1. Import the package.
2. Store a sample sentence.
3. Select a known encoding.
4. encode converts text into integer IDs.
5. len counts the IDs.
6. Decoding each ID separately helps inspect pieces. Pieces may include spaces or fragments.

Use the tokenizer recommended for your chosen model for better estimates.

## 7. Compare with word count
~~~python
sentence = "AI applications can process customer-support messages."
print("Whitespace word count:", len(sentence.split()))
~~~
split() counts whitespace-separated pieces. It is not a tokenizer. Compare the result with the token count and explain why they differ.

## 8. Context budget calculation
Classroom example, not a real model limit:
- Instructions: 700
- History: 1,800
- User question: 300
- Retrieved passages: 3,000
- Output allowance: 1,000
- Planned total: 6,800
- If illustrative capacity is 8,000, remaining headroom is 1,200.

A robust application reserves headroom for formatting and provider-specific overhead. Do not fill the full capacity by default.

## 9. Industry scenario
A learner uploads a long handbook. Sending every page with every question can be expensive and may exceed the context window. Later, document chunking and retrieval will help select relevant passages instead of sending everything.

## 10. Common mistakes
| Mistake | Better approach |
|---|---|
| Token equals word | Use the selected model tokenizer |
| Use arbitrary tokenizer | Check model/provider documentation |
| Count only user question | Include instructions, history and context |
| Use full context capacity | Reserve output and overhead |
| Assume all tokens cost the same | Check current pricing |
| Context window means permanent memory | It is not long-term storage |

2. Tokenization creates: A SQL rows B token IDs C URLs D images. **B.**
3. Context window means: A screen size B token context capacity C database rows D file size. **B.**
4. Budget includes: A only question B instructions/history/input/context/output C only output D only code. **B.**
5. tiktoken is universal: A yes B no. **B:** tokenizers vary.

# 28. Instructor-style walkthrough: designing a safe request budget

Imagine that a learner asks a question about a long course PDF. The backend has already extracted the text and stored sections in a searchable index.

The learner asks: “Explain the difference between supervised and unsupervised learning.”

A poor design sends the entire PDF. A better design follows a sequence:

1. Validate that the question is not empty.
2. Identify the user's permitted course documents.
3. Search for passages relevant to supervised and unsupervised learning.
4. Remove duplicate or clearly irrelevant results.
5. Inspect passage length.
6. Estimate the complete prompt size.
7. Reserve output allowance.
8. Keep a safety margin.
9. If the request is too large, retrieve fewer or shorter passages.
10. Preserve source identifiers for citations.
11. Send the request to the selected model.
12. Inspect the provider response and usage information.
13. Validate the answer and its citations.
14. Record operational metrics without exposing private content unnecessarily.

The design goal is not “send the maximum possible text”. The goal is “send enough relevant, trustworthy context to answer the question”.

## Walkthrough decision table

| Decision | Poor approach | Better approach |
|---|---|---|
| Document selection | Send every document | Restrict to authorised documents |
| Retrieval | Take the first chunks | Rank by relevance and inspect quality |
| Duplicate content | Keep repeated passages | Deduplicate where safe |
| Budget | Count only the question | Account for the complete request |
| Output | Use an arbitrary tiny limit | Reserve enough for the requested answer |
| Overflow | Cut the prompt at a random character | Retrieve, summarise or split meaningfully |
| Verification | Assume the estimate is exact | Compare with tokenizer/provider usage |
| Citations | Drop source IDs | Preserve source metadata |

## Walkthrough questions

**Question:** Why not always choose the largest context window available?

**Answer:** Capacity alone does not determine the best model. Cost, latency, quality, availability, privacy, retrieval quality and output requirements also matter.

**Question:** If the request fits, does that prove the answer will be correct?

**Answer:** No. A context-budget check only addresses request size. It does not prove that the retrieved evidence is relevant or that the model's answer is factual.

**Question:** If a model accepts a large request, should the application send every document?

**Answer:** No. Unnecessary context can reduce relevance, increase cost and latency, and make evaluation harder.
