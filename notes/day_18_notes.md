## 2. Normal response vs streaming response

**Normal response:** The program waits until the model finishes, then receives the complete answer.

**Streaming response:** The program receives pieces of the answer as they are generated.

~~~text
NORMAL
Question -> wait -> complete answer -> display

STREAMING
Question -> piece 1 -> piece 2 -> piece 3 -> finish
                         display as pieces arrive
~~~

| Feature | Normal response | Streaming |
|---|---|---|
| First visible text | Usually after generation completes | Can appear before completion |
| User experience | May feel like waiting | More interactive |
| Code | Read final response | Iterate over incoming events |
| Common use | Short tasks, batch processing | Chat interfaces, longer answers |

Streaming does not necessarily make the model generate faster. It changes when the user sees the output.

## 3. Message roles

A conversation is commonly represented as a sequence of messages.

| Role | Meaning | Example |
|---|---|---|
| system | High-level behavior instructions; provider conventions can differ | Answer in simple language |
| user | Message sent by the person using the application | What is Python? |
| assistant | Response generated by the model | Python is a programming language |

Example:

~~~text
system: You are a beginner-friendly Python tutor.
user: What is a variable?
assistant: A variable is a named place to store a value.
user: Give me an example.
assistant: age = 20
~~~

The model can use earlier messages only when the application/provider includes or otherwise makes that context available. Do not assume a new API request automatically remembers an earlier request.

## 4. Store conversation history in Python

A list can hold dictionaries, with one dictionary per message.

~~~python
messages = [
    {
        "role": "system",
        "content": "You are a beginner-friendly Python tutor."
    }
]

messages.append({
    "role": "user",
    "content": "What is a variable?"
})

messages.append({
    "role": "assistant",
    "content": "A variable is a named place to store a value."
})

print(messages)
~~~

**Expected result:** A list containing three message dictionaries.

### Understand append()

| Property | Explanation |
|---|---|
| Purpose | Adds one item to the end of a list |
| Syntax | list_name.append(item) |
| Argument | The single item to add |
| Return value | None |
| Changes original list? | Yes |

Common mistake:

~~~python
messages = messages.append({"role": "user", "content": "Hello"})
~~~

This is wrong because append() returns None, so messages would no longer refer to the list.

Correct:

~~~python
messages.append({"role": "user", "content": "Hello"})
~~~

## 5. Send conversation history to OpenAI

The following example uses the OpenAI Responses API and includes earlier messages in the next request.

~~~python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

conversation = [
    {
        "role": "system",
        "content": "You are a helpful tutor. Use simple language."
    }
]

def ask_ai(question):
    conversation.append({
        "role": "user",
        "content": question
    })

    response = client.responses.create(
        model="gpt-4.1-mini",
        input=conversation
    )

    answer = response.output_text

    conversation.append({
        "role": "assistant",
        "content": answer
    })

    return answer

print(ask_ai("What is a Python variable?"))
print(ask_ai("Show me a small example."))
~~~

**What happens?**
1. First question is added to the list.
2. Application sends the list to the model.
3. Answer is added as an assistant message.
4. Second question is added.
5. Earlier messages plus the new question are sent.
6. The model can use the earlier exchange to understand the follow-up.

Exact wording varies.

| Code | Explanation |
|---|---|
| def ask_ai(question) | Defines a function with one parameter |
| conversation.append(...) | Adds a message to the existing list |
| input=conversation | Sends conversation messages as request input |
| return answer | Sends the answer value back to the caller |

For a production application, do not use one global conversation list for all users. Each user/session needs isolated history.

## 6. Stream an OpenAI response

A streaming request returns events as output is generated.

~~~python
import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

stream = client.responses.create(
    model="gpt-4.1-mini",
    input="Explain three uses of Python in AI.",
    stream=True
)

for event in stream:
    if event.type == "response.output_text.delta":
        print(event.delta, end="", flush=True)

print()
~~~

**Expected result:** The answer appears progressively in the terminal. Exact chunks and wording vary.

| Code | Meaning |
|---|---|
| stream=True | Requests a streamed response |
| for event in stream | Processes each event as it arrives |
| event.type | Identifies the event type |
| event.delta | Contains a newly generated text piece for this event |
| end="" | Prints without adding a newline after every piece |
| flush=True | Flushes buffered output so it appears promptly |

A stream may include events other than text. Check the event type before reading delta.

## 7. Conversation history has a limit

Each model has a context window. The conversation cannot grow forever.

~~~text
Message 1 + Message 2 + Message 3 + New question
                       |
                       v
              Context window capacity
                       |
           +-----------+-----------+
           |                       |
       Fits in window         Too much content
           |                       |
      Send request           Trim/summarize history
~~~

A long-running chatbot may:
- Keep only recent relevant messages.
- Summarize older conversation.
- Limit the size of user inputs.
- Avoid storing unnecessary personal information.
- Keep user sessions separate.

History is application data. Decide where it is stored, how long it is retained and who can access it.

**Goal:** Build a terminal chatbot that remembers the current session and streams answers.

Required features:
1. Show a welcome message.
2. Accept a question from the user.
3. Store the user message in a history list.
4. Send history to the model.
5. Stream the answer.

## 9. Common mistakes
- Expecting the model to remember earlier API requests without sending history.
- Forgetting to save the assistant response.
- Sharing one user's history with another user.
- Replacing a list with the return value of append().
- Treating every streaming event as a text event.
- Printing every chunk on a new line unintentionally.
- Allowing history to grow without limits.

## 10. Practice with answers
1. **What is streaming?** Receiving output in pieces as it is generated.
2. **Does streaming guarantee faster generation?** No; it can make first text visible earlier.
3. **What is a user message?** A message supplied by the person using the application.
4. **Why send conversation history?** So the model can use relevant earlier messages.
5. **Does an API automatically remember every past request?** Not necessarily; the application must provide history or use a provider state feature.
6. **What does append() return?** None.
7. **What does end="" do in print()?** It prevents a newline after that print call.
8. **Why separate history by session?** To prevent one user's conversation leaking into another's.
9. **Why limit history?** Context windows and cost are limited.
10. **What should be saved after streaming finishes?** The complete assistant response, if future turns need it.
