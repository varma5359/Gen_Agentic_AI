## First FastAPI application
```python
from fastapi import FastAPI

app = FastAPI(title="TechPhile LLM API")

@app.get("/health")
def health_check():
    return {"status": "ok"}
```
- Import `FastAPI` from the installed framework.
- `FastAPI(...)` creates the application object.
- The decorator registers a GET route at `/health`.
- The function returns a Python dictionary that FastAPI serializes as JSON.
- A health endpoint should not make a paid LLM call on every probe.

## Define request and response models
```python
from pydantic import BaseModel, Field

class GenerateRequest(BaseModel):
    prompt: str = Field(min_length=1, max_length=8000)

class GenerateResponse(BaseModel):
    answer: str
    provider: str
    model: str
    request_id: str | None = None
```
- `GenerateRequest` describes the incoming JSON body.
- `min_length` rejects an empty prompt; `max_length` limits this demo's input size.
- The character limit is an application safeguard, not an exact token count.
- `GenerateResponse` documents the public response shape.
- Optional metadata uses `None` when the provider does not return a value.

## Add a route with a service boundary
```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class GenerateRequest(BaseModel):
    prompt: str = Field(min_length=1, max_length=8000)

class GenerateResponse(BaseModel):
    answer: str
    provider: str
    model: str

def generate_answer(prompt: str) -> GenerateResponse:
    # Replace this fake implementation with the application service.
    return GenerateResponse(
        answer=f"Demo response for: {prompt}",
        provider="fake",
        model="offline-demo",
    )

@app.post("/api/generate", response_model=GenerateResponse)
def generate(request: GenerateRequest):
    return generate_answer(request.prompt)
```
- The function `generate_answer` is a service placeholder for offline development.
- The route accepts a validated Pydantic request object.
- The route delegates the use case instead of calling an SDK directly.
- `response_model` documents and validates the response shape.
- The fake answer is not a real model result; it proves the API contract only.

## Test the API contract
```python
from fastapi.testclient import TestClient
from main import app

client = TestClient(app)

def test_health():
    response = client.get("/health")
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}

def test_generate_rejects_empty_prompt():
    response = client.post("/api/generate", json={"prompt": ""})
    assert response.status_code == 422
```
- `TestClient` sends requests to the application in tests without a public server.
- `response.status_code` is the HTTP status.
- `response.json()` parses the response body.
- The empty prompt should be rejected by request validation before the service runs.
- Tests should not require an API key or call a paid provider.

## Add the real provider safely
- Keep the provider SDK call inside an adapter module.
- Read the provider key from server-side environment configuration.
- Validate model identifiers and supported parameters.
- Normalize the response into an internal result object.
- Translate provider exceptions into application error categories.
- Keep provider usage and request IDs optional when not returned.
- Use current official SDK documentation for exact methods and model identifiers.
- Do not return raw SDK objects or raw exception text from the route.

- Keep provider credentials on the server.
- Authenticate callers before expensive generation requests.
- Authorize access to conversation or user-owned resources.
- Configure CORS for known frontend origins only.
- Apply request and output limits.
- Apply rate limits and concurrency controls.

## Troubleshooting
| Symptom | Likely cause | Check |
|---|---|---|
| 404 route | Wrong path or router not included | Inspect OpenAPI route list |
| 422 response | Request body does not match schema | Read safe field validation details |
| 500 response | Unhandled service or configuration error | Check restricted server logs and correlation ID |
| Provider key missing | Deployment secret not configured | Inspect variable name without printing value |
| Browser CORS error | Origin not allowed | Check exact scheme, host and port |
| Slow response | Provider latency or blocking SDK call | Measure route and provider timing |
| Duplicate cost | Client retry or repeated submission | Add request tracking and idempotency policy |
| Leaked secret | Debug logging or frontend configuration | Rotate key and audit logs/build artifacts |

## Exercises with answers
**Exercise 1:** Why should the browser call FastAPI rather than the provider directly using a secret key?
**Answer:** Browser code is visible to users. The backend keeps the provider key in a controlled environment and enforces authentication, authorization, validation, rate limits and cost policies.

**Exercise 2:** What does `response_model` do?
**Answer:** It declares the expected public response shape and lets FastAPI validate and document the response.

**Exercise 3:** Does CORS authenticate a user?
**Answer:** No. CORS is a browser cross-origin policy. Authentication and authorization must be implemented separately.

**Exercise 4:** Why mock the service in route tests?
**Answer:** It makes tests deterministic, fast and free of provider credentials while checking HTTP behavior and schema contracts.

**Exercise 5:** Why can an async route still block?
**Answer:** If it calls a blocking synchronous SDK function directly, that operation can block the event loop. Use a supported async client or a deliberate thread boundary.

## Daily MCQs
1. Where should a provider API key live? **Answer: Server-side configuration or a secret manager.** Browser code is visible to users.
2. What does a Pydantic request model do? **Answer: Validates the incoming request shape and constraints.**
3. What does CORS provide? **Answer: Browser cross-origin access control, not authentication.**
4. Why inject a service dependency? **Answer: To separate route logic and make the service replaceable in tests.**
5. What should a route return when the provider fails? **Answer: A documented safe error response with an appropriate status code.**

## Interview questions
**Q1. Describe the architecture of an LLM-powered FastAPI endpoint.**
**Answer:** The client sends a validated HTTP request. FastAPI authenticates and validates it, the route calls an application service, the service selects a provider adapter, the adapter invokes the SDK and normalizes the response, and the route returns a typed response or safe error.

**Q2. Why separate routes, services and adapters?**
**Answer:** Routes handle HTTP concerns, services implement business use cases and adapters handle provider-specific SDK details. Separation improves reuse, testing and provider replacement.

**Q3. How do you secure an LLM API?**
**Answer:** Keep provider keys server-side, authenticate callers, authorize access to user-owned resources, validate and limit input, apply rate and concurrency limits, use HTTPS, redact logs and test error responses for leakage.

**Q4. Explain CORS versus authentication.
**Answer:** CORS controls whether browser JavaScript from an origin may read a cross-origin response. Authentication identifies the caller. Authorization determines what that caller may access. They solve different problems.

**Q5. How do you test a route without a live LLM?**
**Answer:** Inject or override the service dependency with a fake implementation. Test request validation, response schema, status codes and error mapping. Keep a separate optional smoke test for the real provider.

## Deep-dive 1: Why put an LLM behind an API

A backend API lets a browser, mobile app or another service use the LLM capability without receiving the provider secret.

**Practical behavior:** The backend authenticates the caller, validates input, applies business rules and calls the provider.

**Design decision:** It also centralizes logging, rate limiting, usage controls and error handling.

**Failure mode:** The route should not contain every provider detail.

**Implementation guidance:** A service layer makes the same use case reusable from CLI, tests and other routes.

**Test case:** A public API must enforce authorization and request limits.

**Project connection:** Never call a paid provider directly from browser code with a server secret.

**Operational consideration:** Document the API contract for frontend developers.

**Remember:** An LLM endpoint is a normal software API with an external probabilistic dependency.

## Deep-dive 2: FastAPI overview

FastAPI is a Python framework for building HTTP APIs.

**Practical behavior:** A route maps an HTTP method and path to a Python function.

**Design decision:** Type annotations help FastAPI validate and document request and response data.

**Failure mode:** FastAPI builds interactive API documentation from the application schema.

**Implementation guidance:** The application can use synchronous or asynchronous endpoint functions depending on dependencies and workload.

**Test case:** Do not assume an async route makes a synchronous SDK call non-blocking.

**Project connection:** Use a tested version of FastAPI and its compatible dependencies.

**Operational consideration:** Keep endpoint functions small and delegate business logic.

**Remember:** Read the installed FastAPI documentation for version-specific behavior.

## Deep-dive 3: HTTP method and route

A POST route is commonly used to submit a prompt for processing.

**Practical behavior:** A path such as `/api/chat` identifies the resource or operation.

**Design decision:** The request body contains validated input fields.

**Failure mode:** The route returns a response with a documented status and schema.

**Implementation guidance:** Do not use GET query strings for large or sensitive prompt bodies.

**Test case:** Choose status codes consistently for validation, authentication, throttling and server failures.

**Project connection:** Do not expose provider raw errors as HTTP responses.

**Operational consideration:** Version public API paths when breaking changes are expected.

**Remember:** Test method and path behavior using FastAPI's test client.

## Deep-dive 4: Pydantic request model

A request model defines what the client is allowed to send.

**Practical behavior:** Fields should have types, descriptions and reasonable constraints.

**Design decision:** Reject empty prompts before provider traffic.

**Failure mode:** Set maximum input lengths to control abuse and cost.

**Implementation guidance:** Do not let the client choose arbitrary privileged system instructions.

**Test case:** Keep model selection allowlisted or server-configured.

**Project connection:** Validate optional conversation IDs and other references.

**Operational consideration:** Pydantic validation errors can be converted to a standard API response.

**Remember:** Request models are a security and usability boundary.

## Deep-dive 5: Pydantic response model

A response model defines what the API returns to the caller.

**Practical behavior:** Return only fields the client needs.

**Design decision:** Do not include API keys, internal stack traces or private provider metadata.

**Failure mode:** Use explicit fields for answer, provider/model where appropriate, request ID and status.

**Implementation guidance:** Represent optional usage metadata honestly.

**Test case:** Do not expose internal prompt templates unless the product requires it.

**Project connection:** A response model helps keep the contract stable.

**Operational consideration:** Test that sensitive fields are absent.

**Remember:** Response models are part of API design, not just documentation.

## Deep-dive 6: Dependency injection

FastAPI dependencies provide reusable values or checks to route functions.

**Practical behavior:** They can supply authenticated user information, settings or a service object.

**Design decision:** A dependency should have one clear responsibility.

**Failure mode:** Do not create a new provider client for every tiny operation without understanding its lifecycle.

**Implementation guidance:** Inject a fake service in tests so no live provider is called.

**Test case:** Keep secrets in server configuration, not dependency parameters supplied by clients.

**Project connection:** Use dependency overrides for isolated tests where appropriate.

**Operational consideration:** Avoid hidden global state that makes tests order-dependent.

**Remember:** Dependency injection improves testability and separation.

## Deep-dive 7: Application settings

Settings centralize model name, provider choice, timeout and other runtime configuration.

**Practical behavior:** Validate required settings at startup or before use.

**Design decision:** Keep secrets separate from non-secret operational settings.

**Failure mode:** Use different configuration values for development, test and production.

**Implementation guidance:** Do not return configuration values from a public endpoint.

**Test case:** Allow the deployment platform to inject environment variables.

**Project connection:** Avoid committing `.env` files with credentials.

**Operational consideration:** Test missing and malformed settings.

**Remember:** Configuration should not be scattered through route code.

## Deep-dive 8: Service layer

A service implements the application use case independent of HTTP.

**Practical behavior:** It validates domain rules, calls the provider adapter and returns an internal result.

**Design decision:** It should not read directly from `Request` or print to the terminal.

**Failure mode:** It should raise or return stable application-level errors.

**Implementation guidance:** A CLI and API can call the same service.

**Test case:** The service should receive dependencies explicitly where practical.

**Project connection:** Unit-test it with a fake provider.

**Operational consideration:** Do not place every feature in one giant service function.

**Remember:** A clean service boundary simplifies later streaming, RAG and agent integrations.

## Deep-dive 9: Provider adapter

The adapter translates internal requests to the selected SDK.

**Practical behavior:** It owns provider-specific model names, messages, parameters and response parsing.

**Design decision:** It maps provider exceptions into stable internal categories.

**Failure mode:** It does not decide HTTP status codes.

**Implementation guidance:** It should not know about FastAPI request objects.

**Test case:** Keep provider-specific imports and tests near the adapter.

**Project connection:** Normalize only the fields the service needs.

**Operational consideration:** Verify SDK method names and model support in current provider documentation.

**Remember:** An adapter lets the backend change providers without rewriting routes.

## Deep-dive 10: Synchronous versus asynchronous

A synchronous function waits for an operation to finish before continuing in that thread.

**Practical behavior:** An asynchronous function can await supported I/O and allow the event loop to serve other work.

**Design decision:** An async route calling a blocking synchronous SDK may still block the event loop.

**Failure mode:** Use the provider SDK's async client when it is supported and suitable.

**Implementation guidance:** Do not call `asyncio.run` inside an already-running FastAPI event loop.

**Test case:** Avoid mixing sync and async code without a clear boundary.

**Project connection:** Use concurrency limits for external provider calls.

**Operational consideration:** Test behavior under concurrent requests.

**Remember:** Async is a tool for I/O concurrency, not a guarantee of faster model inference.

## Deep-dive 11: Request lifecycle

The client sends an HTTP request to the backend.

**Practical behavior:** The framework parses and validates the body.

**Design decision:** Authentication and authorization checks run.

**Failure mode:** The route calls the service.

**Implementation guidance:** The service applies business rules and selects the provider adapter.

**Test case:** The adapter calls the provider and normalizes the result.

**Project connection:** The route maps the result to the response schema.

**Operational consideration:** The framework serializes the response and sends it to the client.

**Remember:** Failures must follow the same documented error contract.

## Deep-dive 12: HTTP status codes

A successful request commonly returns a 2xx status.

**Practical behavior:** A validation problem commonly returns 422 in FastAPI's default request validation behavior.

**Design decision:** 401 indicates authentication is required or invalid, while 403 indicates access is denied under the API's policy.

**Failure mode:** 404 may indicate a resource does not exist or is not visible to the caller.

**Implementation guidance:** 429 is commonly used for throttling or rate limits.

**Test case:** 502 or 503 may represent an upstream provider failure or service unavailability depending on the contract.

**Project connection:** 504 may represent an upstream timeout where appropriate.

**Operational consideration:** Do not map every failure to 200 with an error string.

**Remember:** Document status choices and test them.

## Deep-dive 13: Error response schema

A standard error body can include a stable error code, human-readable message and request ID.

**Practical behavior:** Do not include raw exception messages from the provider without sanitization.

**Design decision:** Keep the same shape across routes.

**Failure mode:** Validation errors may include safe field-level details.

**Implementation guidance:** Do not reveal whether another user's private resource exists unless policy permits it.

**Test case:** Log diagnostic details internally with redaction.

**Project connection:** Use a typed error response model where useful.

**Operational consideration:** Test that no secret appears in error responses.

**Remember:** A predictable error contract makes frontend handling simpler.

## Deep-dive 14: Authentication

Authentication establishes who is calling the API.

**Practical behavior:** A production application may use session authentication, OAuth or bearer tokens depending on its architecture.

**Design decision:** Do not invent an authentication scheme for a demo and claim it is production secure.

**Failure mode:** Protect API routes that can incur provider costs.

**Implementation guidance:** Never place the provider key in a frontend request.

**Test case:** Validate tokens using a supported library or trusted identity provider.

**Project connection:** Use secure cookie settings when using sessions.

**Operational consideration:** Test missing, invalid and expired credentials.

**Remember:** Authentication is separate from provider API-key authentication.

## Deep-dive 15: Authorization

Authorization decides what an authenticated caller may do.

**Practical behavior:** A user should access only conversations and records they are permitted to access.

**Design decision:** Check ownership on the backend for every resource lookup.

**Failure mode:** Do not rely on hidden frontend controls.

**Implementation guidance:** A conversation ID is not proof of permission.

**Test case:** Keep admin-only operations behind explicit role checks.

**Project connection:** Use least privilege for database and provider credentials.

**Operational consideration:** Test cross-user access attempts.

**Remember:** Authorization failures should not leak private data.

## Deep-dive 16: CORS

Cross-Origin Resource Sharing controls which browser origins may read responses from an API.

**Practical behavior:** Configure allowed origins explicitly for known frontend domains.

**Design decision:** Avoid wildcard origins with credentialed requests.

**Failure mode:** CORS is a browser policy, not authentication or authorization.

**Implementation guidance:** A non-browser client is not protected by CORS.

**Test case:** Keep development and production origins separate.

**Project connection:** Review allowed methods and headers.

**Operational consideration:** Test preflight behavior from the intended frontend origin.

**Remember:** Do not use CORS as a substitute for access control.

## Deep-dive 17: Rate limiting

An LLM API can be abused to generate unexpected provider costs.

**Practical behavior:** Apply limits by authenticated user, IP or another reviewed identity dimension.

**Design decision:** A process-local counter is not a global limit across multiple server instances.

**Failure mode:** Use a shared store or gateway for distributed enforcement when needed.

**Implementation guidance:** Return a clear 429 response when the application limit is reached.

**Test case:** Apply limits to both request count and possibly input size or token budget.

**Project connection:** Do not let a caller select their own higher limit.

**Operational consideration:** Monitor rejected requests and legitimate-user impact.

**Remember:** Rate limiting is part of cost and abuse protection.

## Deep-dive 18: Input size and abuse controls

A public prompt endpoint should enforce maximum body size and prompt length.

**Practical behavior:** Validate content type and request shape.

**Design decision:** Limit concurrency and request frequency.

**Failure mode:** Do not accept arbitrary provider endpoint URLs from clients.

**Implementation guidance:** Do not allow clients to submit arbitrary SDK parameters without an allowlist.

**Test case:** Consider request deadlines and cancellation.

**Project connection:** Protect logs from prompt content and secret leakage.

**Operational consideration:** Use authentication or other abuse controls appropriate to the service.

**Remember:** Test oversized and malformed bodies.

## Deep-dive 19: Database integration boundary

Conversation persistence can be added through a repository or data-access layer.

**Practical behavior:** The route should not embed raw SQL statements.

**Design decision:** Use parameterized queries or an ORM safely.

**Failure mode:** Store owner ID, conversation ID, role, content and ordering metadata only as needed.

**Implementation guidance:** Do not persist all prompts by default without a product and privacy reason.

**Test case:** Use transactions for related message writes.

**Project connection:** Apply migrations to evolve the schema.

**Operational consideration:** Test repository behavior separately from provider behavior.

**Remember:** Database persistence is an extension when the basic API contract works.

## Deep-dive 20: Background tasks

Some model operations may take longer than a normal HTTP request should remain open.

**Practical behavior:** A background job can return a job ID and let the client check status later.

**Design decision:** A queue needs persistence, retry policy, expiration and authorization.

**Failure mode:** Do not use a simple in-process background task as a durable job system without understanding process failure.

**Implementation guidance:** The job worker should reuse the same service and provider adapter.

**Test case:** Secure job payloads because they may contain user content.

**Project connection:** Bound queue size and concurrency.

**Operational consideration:** Provide clear queued, running, completed and failed states.

**Remember:** Use synchronous request-response for the first simple Day 20 milestone unless requirements demand a queue.

## Deep-dive 21: Streaming API endpoint

A streaming endpoint returns events progressively rather than one completed JSON body.

**Practical behavior:** The framework needs a streaming response mechanism and a generator or async generator.

**Design decision:** Provider events should be normalized before being sent to the client.

**Failure mode:** Set correct response headers for the chosen protocol.

**Implementation guidance:** Ensure reverse proxies do not buffer the response unintentionally.

**Test case:** Handle client disconnect and provider cleanup.

**Project connection:** Do not mix ordinary JSON response bodies with SSE framing.

**Operational consideration:** Test the deployed path, not only the local test client.

**Remember:** Streaming is an extension if the core Day 20 deliverable focuses on a standard REST endpoint.

## Deep-dive 22: API documentation

FastAPI generates OpenAPI documentation from routes and Pydantic models.

**Practical behavior:** A request schema tells clients what to send.

**Design decision:** A response schema tells clients what to expect.

**Failure mode:** Add summaries and descriptions to routes where they improve understanding.

**Implementation guidance:** Document authentication requirements and error codes.

**Test case:** Do not publish secrets or internal-only endpoints in docs.

**Project connection:** Provide sample requests using placeholders.

**Operational consideration:** Keep documentation synchronized with the implementation.

**Remember:** Test the generated schema for expected paths and fields.

## Deep-dive 23: Testing with TestClient

FastAPI's test tools allow requests to the application without launching a public server.

**Practical behavior:** Use a fake LLM service or dependency override in route tests.

**Design decision:** Test valid input, invalid input and provider failures.

**Failure mode:** Assert status codes and response shapes.

**Implementation guidance:** Test authentication and authorization when implemented.

**Test case:** Do not call a paid provider in the normal unit test suite.

**Project connection:** Use integration tests for the real database layer when present.

**Operational consideration:** Keep live smoke tests optional and separately configured.

**Remember:** A route test should be repeatable on a clean machine.

## Deep-dive 24: Dependency override

A dependency override replaces a production dependency with a test implementation.

**Practical behavior:** A fake service can return a known answer without network traffic.

**Design decision:** The override should be reset after the test to avoid affecting other tests.

**Failure mode:** Do not share mutable fake state across unrelated tests unless intended.

**Implementation guidance:** Test that the route maps service errors to the expected HTTP status.

**Test case:** Use a fixture to manage setup and cleanup.

**Project connection:** Verify the override is actually active by asserting the fake was called.

**Operational consideration:** Dependency overrides make API tests inexpensive and deterministic.

**Remember:** Do not confuse a fake-service test with a provider integration test.

## Deep-dive 25: Pydantic response validation

The response model validates the data the route intends to return.

**Practical behavior:** A missing required response field indicates an application bug.

**Design decision:** Do not weaken the response schema to hide inconsistent service output.

**Failure mode:** Use optional fields only when absence is valid.

**Implementation guidance:** Avoid returning raw provider objects that cannot be serialized predictably.

**Test case:** Test output serialization and null handling.

**Project connection:** Keep public fields stable across versions.

**Operational consideration:** Use a separate internal model when the service needs extra metadata.

**Remember:** Response validation protects the API contract.

## Deep-dive 26: Logging middleware

Middleware can add request IDs or measure request duration across routes.

**Practical behavior:** Do not log request bodies containing prompts by default.

**Design decision:** Ensure correlation IDs are validated or generated by the server.

**Failure mode:** Do not trust client-supplied IDs for authorization.

**Implementation guidance:** Capture response status and safe timing metadata.

**Test case:** Avoid logging authorization headers and cookies.

**Project connection:** Keep middleware small and tested.

**Operational consideration:** Do not duplicate sensitive logs in several layers.

**Remember:** Structured request logs help connect API and provider activity.

## Deep-dive 27: Observability

Observability combines logs, metrics and traces to explain system behavior.

**Practical behavior:** Track request count, latency, error category and provider usage where available.

**Design decision:** Record provider request IDs for support without exposing credentials.

**Failure mode:** Measure provider duration separately from total API duration.

**Implementation guidance:** Track rate-limit responses and fallback events.

**Test case:** Avoid prompt text as metric labels.

**Project connection:** Set retention and access controls for telemetry.

**Operational consideration:** Use dashboards to find patterns, not to infer facts from one request.

**Remember:** Test that instrumentation does not change request behavior.

## Deep-dive 28: Deployment configuration

The deployment environment supplies secrets and non-secret settings.

**Practical behavior:** Do not rely on a local `.env` file being present in production.

**Design decision:** Use a secret manager or platform environment configuration.

**Failure mode:** Set allowed frontend origins for the deployed domain.

**Implementation guidance:** Configure worker count and concurrency based on the application and provider quotas.

**Test case:** Set request timeouts at the application and proxy layers consistently.

**Project connection:** Use HTTPS for public traffic.

**Operational consideration:** Keep debug mode disabled in production.

**Remember:** Test startup with missing required configuration in staging.

## Deep-dive 29: Process lifecycle

A web server process starts, imports the application and handles requests.

**Practical behavior:** Startup validation can detect missing configuration before user traffic arrives.

**Design decision:** Do not make an expensive paid provider call on every startup probe.

**Failure mode:** Handle shutdown so clients and background tasks can close cleanly.

**Implementation guidance:** A process restart clears in-memory state.

**Test case:** Do not store durable conversations only in a global Python list.

**Project connection:** Use a process manager and health checks appropriate to deployment.

**Operational consideration:** Keep secrets out of startup logs.

**Remember:** Test startup and shutdown paths.

## Deep-dive 30: API versioning

A public API contract may be consumed by a frontend or external client.

**Practical behavior:** Changing field names or response shapes can break consumers.

**Design decision:** Use a versioned prefix or another documented compatibility strategy.

**Failure mode:** Additive optional fields are often safer than changing required fields.

**Implementation guidance:** Deprecate old versions with a clear migration period.

**Test case:** Keep request and response models version-specific when needed.

**Project connection:** Test compatibility against representative clients.

**Operational consideration:** Do not version every internal helper function.

**Remember:** Versioning is about consumer contracts.

## Deep-dive 31: Frontend integration

The frontend sends a request to the backend route.

**Practical behavior:** The browser must not contain the provider API key.

**Design decision:** Show loading and error states while waiting.

**Failure mode:** Validate input in the frontend for user experience, but validate again on the backend for security.

**Implementation guidance:** Handle HTTP status codes and the documented error response shape.

**Test case:** Avoid rendering model text as trusted HTML.

**Project connection:** Set CORS to the exact frontend origin where appropriate.

**Operational consideration:** Do not store sensitive prompts in browser logs or analytics by default.

**Remember:** Test network failures and expired sessions.

## Deep-dive 32: API contract tests

A contract test checks the documented request and response shape.

**Practical behavior:** Use fixed examples to ensure field names and types remain stable.

**Design decision:** Test error responses as carefully as success responses.

**Failure mode:** Check that OpenAPI contains the expected path and schema.

**Implementation guidance:** Use contract tests when frontend and backend are developed independently.

**Test case:** Do not test only the implementation's private helper functions.

**Project connection:** Keep test examples free of real personal data.

**Operational consideration:** Run contract tests in CI.

**Remember:** A stable contract reduces integration defects.

## Deep-dive 33: Database transactions

A transaction groups related database operations into one logical unit.

**Practical behavior:** If storing a user message and a generation record, decide whether they should commit together.

**Design decision:** If generation later fails, represent the failed state explicitly rather than leaving misleading records.

**Failure mode:** Use the ORM or database driver's transaction API correctly.

**Implementation guidance:** Do not keep a database transaction open during a long model call unless there is a compelling design reason.

**Test case:** Commit or roll back intentionally.

**Project connection:** Test failure between writes.

**Operational consideration:** Use migrations for schema changes.

**Remember:** Transactions protect consistency but do not make provider calls transactional.

## Deep-dive 34: Secrets in web applications

A backend secret is not safe if the frontend can download it.

**Practical behavior:** Do not return environment settings from a diagnostic route.

**Design decision:** Do not expose SDK client objects or credential strings in debug output.

**Failure mode:** Restrict environment access to the service process.

**Implementation guidance:** Rotate keys after exposure.

**Test case:** Use separate development and production credentials.

**Project connection:** Use least privilege and usage monitoring where supported.

**Operational consideration:** Test that public responses and logs do not contain fake secret markers.

**Remember:** Secret handling must be reviewed end to end.

## Deep-dive 35: Prompt injection at API boundary

A public API receives untrusted text from callers.

**Practical behavior:** A caller may include instructions that conflict with application behavior.

**Design decision:** Keep system instructions server-controlled and separate from user text.

**Failure mode:** Do not use prompt wording as an authorization mechanism.

**Implementation guidance:** Validate data and enforce permissions in ordinary code.

**Test case:** Treat model responses as untrusted before storing or rendering them.

**Project connection:** Do not execute generated code or SQL.

**Operational consideration:** Add adversarial input fixtures to tests.

**Remember:** Security controls should not depend on the model obeying a prompt.

## Deep-dive 36: Cost controls

Each API request can trigger provider usage.

**Practical behavior:** Limit input length, output size, concurrency and request frequency.

**Design decision:** Allowlist model identifiers rather than letting a caller choose any model.

**Failure mode:** Set budgets and alerts in the provider account where available.

**Implementation guidance:** Track usage metadata if the provider reports it.

**Test case:** Do not hardcode pricing without checking the current pricing page and date.

**Project connection:** Reject unauthenticated or abusive traffic before provider calls.

**Operational consideration:** A timeout or retry may still incur cost.

**Remember:** Cost controls belong at the backend boundary.

## Deep-dive 37: API smoke testing

A smoke test checks that the deployed API can perform a small expected operation.

**Practical behavior:** Use a harmless prompt and a controlled account.

**Design decision:** Do not run a large batch against production merely to verify connectivity.

**Failure mode:** Check response status, response schema and safe logs.

**Implementation guidance:** Confirm that secrets are configured in the deployment environment.

**Test case:** Record model identifier and test time.

**Project connection:** Keep smoke tests separate from unit tests.

**Operational consideration:** Do not expose a public unauthenticated diagnostic endpoint that makes paid calls.

**Remember:** A successful smoke test is one signal, not full production validation.

## Deep-dive 38: Error mapping

Map internal error categories to consistent HTTP status codes.

**Practical behavior:** Invalid input maps to a client error.

**Design decision:** Missing or invalid caller authentication maps to an authentication response.

**Failure mode:** Insufficient permission maps to a forbidden response.

**Implementation guidance:** Application throttling maps to a rate-limit response.

**Test case:** An upstream provider outage may map to a gateway or service-unavailable response depending on the contract.

**Project connection:** An upstream timeout may map to a gateway timeout where appropriate.

**Operational consideration:** Do not return HTTP 200 for every failure.

**Remember:** Test every mapping.

## Deep-dive 39: Modular project structure

Keep application creation in an app factory or small main module.

**Practical behavior:** Keep API routes in a router module as the application grows.

**Design decision:** Keep Pydantic schemas separate from provider SDK code.

**Failure mode:** Keep services independent of HTTP.

**Implementation guidance:** Keep configuration centralized.

**Test case:** Keep tests grouped by layer.

**Project connection:** Avoid circular imports by defining clear dependency directions.

**Operational consideration:** Do not create dozens of empty modules for a tiny exercise.

**Remember:** The structure should make responsibilities obvious to a beginner.

## Deep-dive 40: API documentation and examples

Include a minimal valid request body.

**Practical behavior:** Include a representative success response with fictional content.

**Design decision:** Include validation and provider error examples.

**Failure mode:** Document which fields are optional.

**Implementation guidance:** Explain authentication and rate limits.

**Test case:** Show how to run locally and how to run tests.

**Project connection:** Use placeholder model names and credentials in examples.

**Operational consideration:** Label illustrative outputs as examples, not guaranteed model results.

**Remember:** A complete README is part of the deliverable.

## Deep-dive 41: Production readiness

A working endpoint is not automatically production-ready.

**Practical behavior:** Production readiness includes authentication, authorization, validation, rate limiting and secret management.

**Design decision:** It also includes timeouts, bounded retries, observability and deployment health checks.

**Failure mode:** Review data retention and privacy before storing prompts.

**Implementation guidance:** Use a tested dependency set and reproducible deployment.

**Test case:** Test failure behavior and provider outage paths.

**Project connection:** Document incident response and operational ownership.

**Operational consideration:** Do not claim compliance or security certification without evidence.

**Remember:** List known limitations honestly.

## Deep-dive 42: Interview explanation

Explain why the provider key must remain on the backend.

**Design decision:** Explain request and response Pydantic models.

**Failure mode:** Describe why the route calls a service instead of an SDK directly.

**Implementation guidance:** Explain sync versus async behavior.

**Test case:** Describe authentication, authorization, CORS and rate limiting as different controls.

**Project connection:** Explain how you mock the provider in route tests.

**Operational consideration:** Describe how provider errors map to HTTP status codes.

**Remember:** Explain how deployment secrets and logs are protected.
